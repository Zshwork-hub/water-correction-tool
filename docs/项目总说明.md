## 1. 项目是什么

项目名称：水系栅格数据可视化订正工具

目标：
- 对河道栅格 `ASC` 进行人工可视化订正
- 对流向栅格 `ASC` 进行人工可视化订正
- 以水系 `SHP` 作为参考辅助
- 保持 Windows 桌面可运行、可导出、可回退、可恢复

当前交付状态：

## 2. 用户目标和使用方式

用户最常做的事：
- 加载河道 `ASC`
- 加载流向 `ASC`
- 加载河流 `SHP`
- 切换河道/流向模式
- 在地图上点击、拖动、刷写、修改
- 预览后再应用
- 导出修改后的 `ASC`

这个工具不是自动解算器，而是“人主导、程序辅助”的编辑器。

### 5.4 流向辅助

当前思路：
- 先用 SHP 参考线做矢量批量修正，再人工补改河道栅格
- 右键单点选择一个河道像元时，点击“锁定选区河道”会锁定该像元所在的局部连通河段
- 右键拖框时，点击“锁定选区河道”会锁定框内全部 `Stream=1` 河道像元
- 如果只想补充一个遗漏的河道像元，右键单点后点击“补锁单像元”
- 如果锁定范围局部选错，右键单点或拖框后点击“清除选区”，只清除选区内的锁定，其他锁定保留
- 锁定河道后，右键单点选中本段下游出口，点击“设为出口”
- 点击“预览河道流向”时，程序在锁定河道像元上建立 8 邻域连通图，从出口反推加权图距离，让河道像元指向通往出口的相邻河道像元
- 加权距离中横竖方向成本低于斜向方向；斜向旁边存在正交河道像元时会增加角切惩罚，减少交汇处不合理斜切
- 河道本体流向新增计算模式：
  - “平滑”：默认模式，连续斜向河段更容易保留东南/西南/西北/东北方向，同时仍抑制孤立交汇斜切
  - “稳健”：更强地避免交汇斜切，结果会更偏东西南北四向
- 流向辅助 UI 已按流程重排为 4 组：选择与锁定、河道本体流向、周边汇流、应用与清理
- 出口像元本身不强制改方向，出口之后的下游方向仍由人工按实际情况处理
- 应用河道本体流向会写入当前内存中的流向栅格，并自动切换到“订正流向”模式，之后导出 ASC 才会导出流向结果
- 应用河道本体流向后，再预览和应用周边汇流
- “应用”按钮按当前预览类型动态变化：河道本体预览显示“应用河道流向”，周边汇流预览显示“应用周边汇流”
- 顶部不再放重复的流向预览/应用按钮，流向辅助相关动作集中在右侧 4 步流程中
- 选区或出口选错较多时，点击“清空锁定”会清除全部锁定河道、出口和当前预览
- 后续流向辅助只负责周边非河道像元，不覆盖已锁定的河道本体
- 周边像元优先朝最近的河道骨架像元收敛，而不是简单围绕单点吸附
- 缓冲汇流只围绕已锁定选区的局部外包框计算，不应扫描或修改全国范围
- 如果河道栅格再次编辑，旧的锁定状态会被清空，避免用过期骨架修 FDR

这块的目标是辅助人工，而不是完全自动求解。

## 13. V2.1 计划：面 SHP 汇流范围辅助

这个功能暂时不是急需开发项，但已经确定为后续重要增强方向。后续上下文压缩或重新接手时，请优先阅读本节，避免忘记设计意图。

### 13.1 目标

新增一个独立的“汇流范围 SHP”图层，用面状 Shapefile 限定周边汇流处理范围。它不替代当前河流参考线 SHP，也不影响河道批量修正用的线 SHP。

参考面 SHP：
- `C:\Users\86176\Desktop\水系订正\重庆\重庆市.shp`

目标工作流：
1. 导入河道 ASC、流向 ASC、河流参考线 SHP。
2. 依据河流参考线完成河道订正。
3. 导入汇流范围面 SHP。
4. 显示面边界。
5. 一键锁定位于面内的已订正河道骨架。
6. 预览面内非河道像元向最近锁定河道汇流。
7. 人工检查后应用到 FDR。

### 13.2 功能要求

- 新增“汇流范围 SHP”图层，和当前河流参考线 SHP 分开管理。
- 支持面要素 Polygon，不覆盖现有线 SHP。
- 地图上显示面 SHP 边界，已支持独立颜色和线宽调节，与河流线 SHP 颜色分开。
- 周边汇流模式增加选项：远近带模式、面范围模式；面范围模式已支持最大距离限制。
- 支持一键直接锁定位于面内的所有 `Stream = 1` 河道骨架。
- 面内如果有多个河道骨架，默认让像元汇入最近河道。
- 后续支持指定河道：只让面内像元汇入用户指定的锁定河道。
- 面和 ASC 坐标系不一致时，复用现有投影转换逻辑。
- 阶段一显示已支持多条边界环；后续参与面范围汇流计算时，复杂 multipart/孔洞语义需要再单独谨慎处理。

### 13.3 覆盖策略设想

面内已有流向是否覆盖，后续不要简单“一律覆盖”。建议提供覆盖策略：
- 全部重算。
- 仅修改 NODATA。
- 仅修改未汇入锁定河道的像元。

默认建议为“仅修改未汇入锁定河道的像元”。“合理流向”的初步判定可以采用拓扑近似：沿当前 D8 流向追踪若干步，如果能进入已锁定河道骨架，则认为相对合理；如果流出面范围、进入 NODATA、循环或无法到达锁定河道，则认为需要修正。

### 13.4 实现阶段建议

阶段一：面 SHP 加载与显示。
- 读取 Polygon SHP。
- 显示边界。
- 显示当前汇流范围文件状态。
- “加载范围SHP”入口归入顶部“文件与项目”，右侧“流向辅助”只保留显示边界和线宽等图层控制。
- 支持显示多条边界环。
- 不参与计算。

阶段二：面内河道锁定。
- 将 polygon 栅格化或做点在面内判断。
- 找出面内 `Stream = 1` 河道像元。
- 一键加入当前锁定河道。
- 显示锁定数量，数量过大时先提示确认。
- 当前实现为“锁定范围内河道”：只锁定当前已订正河道栅格中的 `Stream = 1` 像元，不修改河道或流向数据。
- 多个边界环暂按并集处理；孔洞不做拓扑解释，后续若需要严格面语义再扩展。

阶段三：面范围汇流预览。
- 右侧“周边汇流”新增模式选择：`近远带` 保持原缓冲带逻辑，`范围SHP` 使用汇流范围面。
- 只处理面内非河道、非 NODATA 的有效 FDR 像元。
- `最大距` 只作用于 `范围SHP` 模式，默认 `30` 像元，`0` 表示不限距离。
- 默认汇入最近锁定河道骨架。
- 先预览，不直接应用。
- 河道本体流向预览和周边汇流预览均区分两类箭头：橙色为应用后会修改的像元，蓝色为符合条件但当前方向已一致的像元。
- 复用现有“应用预览”机制。
- 当前实现已接入“范围SHP汇流预览”；如果候选像元超过 200000 个，预览前会提示确认。

阶段四：覆盖策略与导出报告。
- 增加覆盖策略选择。
- 导出报告记录汇流模式、面 SHP 路径、修改像元数量和覆盖策略。

### 13.5 代码结构建议

可能新增或扩展：
- `water_core.py`：新增 `PolygonLayer` 和 `parse_shapefile_polygons()`。
- `water_render.py`：新增面边界叠加绘制。
- `water_flow_assist.py`：新增面范围汇流预览计算。
- `water_app.py`：只负责按钮、状态和流程协调。
- 可选新增 `water_polygon.py`：面 SHP 读取、边界转换、polygon 栅格化或点在面内判断。

### 13.6 风险与约束

- 面 SHP 太大时，面内栅格化和最近河道搜索可能慢。
- 面内有多个流域或多个相邻河道时，最近河道不一定等于真实汇流目标，因此必须保留预览和人工确认。
- 无 DEM 条件下，“合理流向”只能做拓扑近似，不追求完美自动解。
- 默认不覆盖河道本体流向，河道本体流向仍由已有河道流向修正流程确定。
- 该功能应作为 V2.1 核心功能单独开发，不要和其他大改混在一起。阶段一只做加载与显示，不做面内锁定和汇流计算。

## 14. GitHub 工作流

当前 GitHub 仓库：
- `https://github.com/Zshwork-hub/water-correction-tool`

仓库用途：
- GitHub 仓库只管理源代码、打包配置和文档。
- 大型业务数据、构建产物、用户会话、自动保存和导出成果不进入 Git。

应该提交：
- `.py` 源码
- `README.md`
- `requirements.txt`
- `water_correction_tool_v2_1.spec`
- `docs/`
- `.gitignore`

不应该提交：
- `Stream_origin.asc`
- `FDR.asc`
- `重庆/`
- `build/`
- `dist/`
- `user_data/`
- `*.waterproj`
- `*.waterproj.npz`
- `water_correction_log.csv`

日常开发流程：
1. 开始前运行 `git status`，确认当前状态。
2. 如有远程更新，先运行 `git pull`。
3. 修改代码和文档。
4. 本地运行或打包验证。
5. 再运行 `git status` 和必要时运行 `git diff`，确认没有误提交数据。
6. 运行 `git add ...` 暂存明确要提交的文件。
7. 运行 `git commit -m "清楚描述本次改动"`。
8. 运行 `git push` 推送到 GitHub。

提交习惯：
- 修一个明确 bug，提交一次。
- 加一个小功能，提交一次。
- 完成一次 UI 调整，提交一次。
- 打包发布前，提交一次。
- 发布后更新说明文档，提交一次。

发布版本流程：
1. 确认代码稳定并提交到 GitHub。
2. 使用 `water_correction_tool_v2_1.spec` 打包 V2.1 EXE。
3. 在 GitHub Releases 创建版本，例如 `v2.1.0`。
4. 上传 EXE 到 Release 附件，不要把 EXE 直接提交到代码仓库。
5. Release 说明优先参考 `docs/V2.1发布说明.md` 的格式。

后续如果用户要求提交或推送：
- 先检查 `git status`。
- 确认 `.asc`、`SHP`、`dist/`、`build/`、`user_data/` 没有进入暂存区。
- 不要强推，除非用户明确要求并理解风险。
